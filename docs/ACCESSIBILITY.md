# Accessibility behavior and verification

The native exploration canvas normalizes ordinary touch and API20 accessibility hover into the same stable-ID semantic actions as the object list, large buttons and on-screen scanning. A canvas does not hide the entire screen from accessibility. Persistent Library and Stop audio controls remain outside the exploration surface. Coordinate forms and explicit buttons provide alternatives to dragging, zooming and panning gestures.

Boundary hysteresis retains an already focused object across movement of up to two display pixels beyond its exact edge, adjusted for fit and zoom. It does not enlarge the initial target or hide overlapping objects. Clear crossings, touch cancellation and explicit layer selection remain effective. Host regressions cover neighbouring objects, holes, line strokes and zoom; final native regression results are listed separately in the test report.

Settings provide up to 200% text, high contrast, dwell delay, volume, optional vibration, scanning speed and coordination with screen-reader automatic speech. Longer descriptions require an explicit request. Audio is cancelled on foreground loss, mode changes, touch cancellation, interruption and output-device change. Missing vibration is reported without implying that a simulated event was physically felt.

Source review still needs an author who can assess the original or an equivalent accessible reference. A labelled coordinate form does not provide independent access to an undescribed image. An imported author declaration is not accessibility certification.

The following checks were performed against the installed native application on the second OpenHarmony/Oniro emulator (`127.0.0.1:55556`), with its persisted text size at 200%. These are developer interaction tests. HAP hashes and the narrower scope of each observation are recorded in [the UI evidence ledger](evidence/native-ui-observations.json).

The reference emulator has no genuine spoken screen-reader bundle available for the complete flow. The installed native accessibility extension probe demonstrates event delivery only. It is not evidence of successful spoken-reader use or of a blind user's experience. A compatible runtime with a genuine reader must still verify import, acceptance, tutorial, hover exploration, list navigation, answer selection/submission, pause, exit and resumption, in English and at 200% text. Automated UI tests use a test extension; a genuine spoken-reader walkthrough is a separate compatibility check.

Physical vibration, physical headphone removal, simultaneous reader/audio behavior and representative-user usability remain separate unverified checks. No physical haptic effect or acoustic timing is inferred from an emulator capability flag, output callback or captured QEMU stream. No blind/low-vision learner or teacher participant study is claimed. See [the test report](TEST_REPORT.md) for recorded outcomes and compatibility limits.
